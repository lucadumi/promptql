# Train set: text-to-SQL (synthetic, de-leaked from eval)

The **training split** used to LoRA-fine-tune the base model. It is generated by
`src/build_dataset.py` and is kept **strictly separate** from `data/eval` so the
before/after comparison measures real generalisation, not memorisation.

## Files
- `text2sql_train.jsonl` - 451 examples
- `text2sql_val.jsonl` - 60 examples (held out to watch **eval loss** during training)

Record schema is **identical to the eval file** (so `src/data_utils.load_jsonl`
and the same prompt format apply to both), one JSON object per line:
```json
{"id": 1, "question": "How many departments are located in London?", "sql": "SELECT COUNT(*) FROM departments WHERE location = 'London'"}
```

## Fixed schema
Same SQLite schema as eval (see `src/data_utils.py::SCHEMA_SQL`): a `departments`
table and an `employees` table. Every question is written against it.

## How it was built (data curation notes)
- **Template-based synthetic generation.** Each SQL *pattern* the eval set tests
  (projection, `COUNT`/`AVG`/`SUM`/`MAX`/`MIN`, `WHERE` on numbers/strings/dates,
  `ORDER BY`, `LIMIT`, `DISTINCT`, `GROUP BY`, `HAVING`) is a template expanded
  over parameter pools (departments, locations, salary/budget thresholds, hire
  dates, top-N, having-N). This teaches the *skills* with *different questions and
  values* than eval.
- **Several phrasings per SQL target (~3.5 on average).** The first version of this
  set gave every pattern exactly one wording, and the resulting fine-tune scored
  100% on in-template questions but only 75% on reworded ones: it had fit the
  template strings. Every pattern now ships a list of interchangeable phrasings
  that vary register, synonyms and sentence shape ("List the names of ...",
  "Which employees ...", "Name the staff whose ..."), all mapping to the same
  canonical SQL.
- **Canonical SQL style** matches the eval gold and `src/metrics.py` (uppercase
  keywords, single-quoted string literals, no trailing semicolon).
- **No leakage (enforced).** A candidate is dropped if its normalised question
  **or** normalised SQL collides with any eval example. The blocklist is built from
  **every** file in `data/eval` (in-template, paraphrase and cross-schema), not just
  the in-template one, because adding paraphrased training questions would
  otherwise risk colliding with the very set used to measure paraphrase
  robustness. The SQL check reuses `src.metrics.normalize_sql` - the exact function
  used for scoring - so no training target can ever equal a graded eval answer.
  Duplicate questions are also removed.
- **Closeness is measured, not assumed.** The build report prints the highest
  word-overlap between any training question and any eval question. The closest
  pair differs only in a literal (a different threshold, department or limit) and
  its SQL target is absent from every eval set, so it teaches the model to read the
  parameter rather than to recognise the exam.
- **Ambiguous wordings are avoided.** Phrasings are checked for cross-table
  ambiguity: describing `SELECT department FROM employees` as "the departments of
  all employees" taught the model that the word "departments" implies a
  `department` column, and it then answered "List all department names" with
  `SELECT department FROM departments`. Those phrasings now tie the column to a
  single employee ("the department of each employee").
- **Stratified split.** ~10% of *each* pattern is held into the validation file,
  so validation mirrors every SQL construct (a rare pattern is never train-only).
- **Reproducible.** Everything is seeded (`--seed`, default 13); re-running
  `python -m src.build_dataset` reproduces the same files.

Build report (default settings): 576 candidates → 65 dropped as eval-leakage,
0 duplicates → **511 kept** (451 train / 60 val) covering 147 distinct SQL targets
at ~3.5 phrasings each, leakage vs eval **0 (verified)**.

## Regenerate
```bash
python -m src.build_dataset                 # writes both files + prints the report
python -m src.build_dataset --val-frac 0.15 # larger validation split
python -m src.build_dataset --eval-file data/eval/text2sql_eval.jsonl  # de-leak against one set
```

## Important
- This is the **train** split. Never evaluate on it, and never let eval questions
  leak in - the de-leak filter in `src/build_dataset.py` is what guarantees that.
