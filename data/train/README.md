# Train set: text-to-SQL (synthetic, de-leaked from eval)

The **training split** used to LoRA-fine-tune the base model. It is generated by
`src/build_dataset.py` and is kept **strictly separate** from `data/eval` so the
before/after comparison measures real generalisation, not memorisation.

## Files
- `text2sql_train.jsonl` - 150 examples
- `text2sql_val.jsonl` - 26 examples (held out to watch **eval loss** during training)

Record schema is **identical to the eval file** (so `src/data_utils.load_jsonl`
and the same prompt format apply to both), one JSON object per line:
```json
{"id": 1, "question": "How many departments are located in London?", "sql": "SELECT COUNT(*) FROM departments WHERE location = 'London'"}
```

## Fixed schema
Same SQLite schema as eval (see `src/data_utils.py::SCHEMA_SQL`): a `departments`
table and an `employees` table. Every question is written against it.

## How it was built (data curation notes)
- **Template-based synthetic generation.** Each SQL *pattern* the eval set tests
  (projection, `COUNT`/`AVG`/`SUM`/`MAX`/`MIN`, `WHERE` on numbers/strings/dates,
  `ORDER BY`, `LIMIT`, `DISTINCT`, `GROUP BY`, `HAVING`) is a template expanded
  over parameter pools (departments, locations, salary/budget thresholds, hire
  dates, top-N, having-N). This teaches the *skills* with *different questions and
  values* than eval.
- **Canonical SQL style** matches the eval gold and `src/metrics.py` (uppercase
  keywords, single-quoted string literals, no trailing semicolon).
- **No leakage (enforced).** A candidate is dropped if its normalised question
  **or** normalised SQL collides with any eval example. The SQL check reuses
  `src.metrics.normalize_sql` - the exact function used for scoring - so no
  training target can ever equal a graded eval answer. Duplicate questions are
  also removed.
- **Stratified split.** ~10% of *each* pattern is held into the validation file,
  so validation mirrors every SQL construct (a rare pattern is never train-only).
- **Reproducible.** Everything is seeded (`--seed`, default 13); re-running
  `python -m src.build_dataset` reproduces the same files.

Build report (default settings): 194 candidates → 18 dropped as eval-leakage,
0 duplicates → **176 kept** (150 train / 26 val), leakage vs eval **0 (verified)**.

## Regenerate
```bash
python -m src.build_dataset                 # writes both files + prints the report
python -m src.build_dataset --val-frac 0.15 # larger validation split
```

## Important
- This is the **train** split. Never evaluate on it, and never let eval questions
  leak in - the de-leak filter in `src/build_dataset.py` is what guarantees that.
